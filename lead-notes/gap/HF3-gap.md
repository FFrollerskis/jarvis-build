## (A) Sammendrag

- **Ingen MC-fase er ferdig.** Repoet har tenant-/RLS-fundamentet som HF3 forutsetter, og det planen kaller «Organization» er allerede repoets `tenants(kind=business)` (D-21). Mangler: IdP/OIDC/passkey, organisasjons-/medlemskapsmodell med status/limits, org-sesjon med membership/policy_version, device trust_state/distinct-device, Company Lock, per-org vault + Platform Secret Domain + miljøisolasjon, Connections-register (`service_connections`), Model Provider Registry/org-AI-policy/subprocessors, authority_policies + Approval v2, Security Event Plane, hash-kjedet audit med signerte sjekkpunkter, org-lifecycle, portefølje, DR-mål, successions-/kontinuitetspakke.
- **Tellinger (primær status per kravrad, 96 rader; telt med grep mot B-tabellene):** `BUILT_WIRED` = 5, `BUILT_DORMANT` = 1, `PARTIAL` = 37, `NOT_BUILT` = 40, `EXTERNAL` = 7, `GATED_BY_PLAN` = 5, `NOT_TO_BUILD` = 0, `PROGRAM_CONFLICT` = 1 (AU4; + 5 sekundære konflikter PC-2..PC-6 i (E)). Rader med både kodedel og ekstern del er splittet eller merket i merknad. `PARTIAL`-tyngden (37) skyldes at HF3 «utvider» eksisterende komponenter (PolicyGateway, session_grants, person_tenants, devices, Integration Center, ModelGateway-sensitivitet, audit), jf. HF3 §0.2.
- **Viktigste enkeltfunn:**
  1. `apps/api/src/main.ts` kjører **22 distinkte `run*ForAllTenants`-sveip** (ca. 54 `.start(`/scheduler-kall, grep) over ALLE business-tenants med delt pool/credentials (`main.ts:1815-1859`, `023/052` DEFINER-kataloger). Så snart pappas bedrift er en `kind=business`-tenant i samme DB, trekkes den inn i Tobias sine sveip. Dette er HF3-kravet «én org + env + capability per jobb» (MC-9) og den største omstruktureringen.
  2. Authority er **konfigurasjon, ikke DB**: `AuthorityConfig{owner_person_id, owner_tenants}` (`modules/policy/src/authority.ts:42`), statisk `mandates`-Set (`policy-gateway.ts:79,238`), `SOVEREIGN` auto-ALLOW klasse D (`policy-gateway.ts:244`) og `credentialBinding.owner_tenants` (`main.ts:306,456`). HF3 flytter authority til Jarvis-DB (`organization_memberships` + `authority_policies`) og krever at Tobias IKKE er suveren i pappas org.
  3. Minste-risiko-vei finnes: **utvid, ikke dupliser** (HF3 §0.2): `person_tenants` → memberships, `session_grants` → org-sesjon, `SignedApproval` → v2, `devices` → trust_state, `audit_events` → hash-kjede (mønster i `075`), `organizations` (ubrukt tabell) → juridisk org-profil. `org_id` ≡ `tenant_id` (ikke ny kolonne på ~128 tabeller).
  4. HF3 §9.2 «migrasjonskontrakt/CI-lint» er **delvis** bygget: `modules/core/test/remediation-2-schema-invariants.test.ts` (DEFINER-allowlist, FORCE-RLS-dekning, `true`-policyer, scope-FK-baseline TOM) + `d395-erasure-coverage.test.ts` (baseline som bare krymper) + `check:containment`, alt kjørt på hver PR (`.github/workflows/ci.yml`). Mangler klassifiseringsmanifest og negativ A/B-fixture per tabell.
- **Størrelse:** 22 WP-er = 2 S + 11 M + 9 L ≈ 70 lead-økter (spenn 55-90). Planens eget anslag: 20-38 uker (én bygger + AI), MC-1/3/5/7/8/9/10 delvis absorbert i UA/EV-arbeid (§18.1).
