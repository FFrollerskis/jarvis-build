# Audit report: modules/business + modules/growth

Files read: **83/83** (63 business + 20 growth: package.json/tsconfig ×4, src ×27, test ×28 [inc. 1563-line service-rls.test.ts in full], scripts ×22, lib ×2). `tsc --noEmit` clean in both packages.

## A. BUGS / LOGIC HOLES

- **P2** `modules/business/src/business-event-sync.ts:133` — `if (!message.id) continue;` skips Gmail messages lacking an `id` but still counts them in `stats.scanned`; a provider that omits `id` on some messages silently loses them with no `unmatched`/error signal distinguishing "no id" from "no contact match." Fix: increment a distinct `skipped_no_id` counter or log.
- **P2** `modules/business/src/open-loop-service.ts` (`upsertOpenLoop`, throughout) — every rule passes a fresh `randomUUID()` for `open_loop_id` even on the `ON CONFLICT ... DO UPDATE` path, where the generated id is discarded; harmless but wasteful (see D. below) — not a correctness bug, downgraded from earlier read.
- **P3** `modules/business/src/business-event-sync.ts:190-194` (`syncCalendarActivities`) — `counterparts` filters by `.trim().toLowerCase() !== accountEmail...` but doesn't run each attendee through `extractEmailAddress()` first (unlike Gmail path), so a malformed attendee string could pass through as a "counterpart" unvalidated and later fail contact lookup silently as unmatched — not exploitable, just inconsistent with the Gmail path's stricter parsing.
- **P3** `modules/growth/src/service.ts:906` (`generateExecutionCommand`) — `BigInt(Math.round(reductionFraction * 1000))` truncates fraction precision to 3 decimals (0.1%); a `reductionFraction` like `0.12345` silently rounds to `0.123`. Documented nowhere; low impact since only internal proposal math, never sent to a provider.

No tenant/memory-space isolation gaps found — every service method routes through `withMemoryTransaction`, and dozens of dedicated RLS tests (business-service, open-loop-*, scoring-*, growth service-rls) exercise cross-tenant/cross-space denial directly against a non-bypass Postgres role. No untrusted content (email/calendar body) reaches `business_activities.summary` or any prompt — `business-event-sync.ts` explicitly never stores `body_text`, proven by dedicated tests (`business-event-sync.test.ts` §C, `ua3-business-events-live.ts`). No secrets logged — every live script sanitizes with `evaluateSecretSafety`/`.slice()` truncation and tests assert non-leakage.

## C. GAPS

- **P1** `.env.example` is missing several env vars this slice reads: `JARVIS_BUSINESS_SWEEP_HOUR`, `JARVIS_BUSINESS_WEEKLY_BRIEF_HOUR`, `JARVIS_BUSINESS_WEEKLY_BRIEF_WEEKDAY`, `JARVIS_BUSINESS_EVENTS_SYNC_HOUR`, `JARVIS_BUSINESS_SCORING_HOUR`, `JARVIS_GROWTH_RECOMMENDATION_SWEEP_HOUR` (all read via `process.env[...] ?? default` in `apps/api/src/main.ts` for `DailyScheduler` hours — confirmed via grep, defaults exist so this is non-fatal but undocumented for operators). `JARVIS_BUSINESS_INTERNAL_TOKEN` correctly absent (sentinel, never a real env var — documented in `credential.ts`/`RUNTIME_GATES.md`). Fix: add commented entries with defaults to `.env.example`.
- **P2** `modules/business/src/open-loop-service.ts` — D-227 pattern (every per-item catch must log+count) is honored at the **sweep level** (`open-loop-sweep.ts`, `business-event-sync.ts`, `scoring-sweep.ts`, `action-recommendation-sweep.ts` all log+zero-out per-tenant failures), but *within* a single tenant's `runSweep()`, each of the ~25 detection rules is `await`-ed sequentially with **no try/catch per rule** (`open-loop-service.ts:890-951`). One rule throwing (e.g. a missing table for a not-yet-migrated domain) aborts the whole sweep for that tenant, and no per-rule count is surfaced — only whole-tenant success/failure. This is weaker than the D-227 discipline applied one level up. Fix: wrap each detect* call in the `runSweep` array with its own try/catch, accumulate errors, and never let one rule's exception mask the rest.
- **P3** `modules/growth/src/service.ts` `campaignPerformance()`/`computePerformanceSnapshot()` — non-trivial multi-join SQL with real business logic (fan-out avoidance for meetings) is well covered by dedicated tests (§G, §Q in service-rls.test.ts) — no gap here, noted only because it was the area most likely to have one.
- **P3** No test found asserting that `OpenLoopService.runSweep()` itself does NOT let one rule's throw abort the others (contrast with the sweep-level tests, which only cover the outer `runOpenLoopSweepForAllTenants` isolation, not intra-tenant intra-sweep isolation) — this is the gap counterpart to the C-P2 finding above.

- **P3** `modules/business/src/open-loop-service.ts` — ~25 near-identical `detect*` methods each hand-build the same `UpsertOpenLoopInput` object with 12+ null fields; a small builder/defaults helper (`baseOpenLoopFields(overrides)`) would cut ~150 lines of repetition and reduce risk of a copy-paste field omission in a future rule.
- **P3** `modules/business/src/open-loop-service.ts` / `modules/growth/src/service.ts` — `detectSpendAnomalies()` (business) and `detectAndRecommendSpendAnomalies()` (growth) run the **identical** trailing-7-day-average SQL against `marketing_spend_events`, duplicated by design per the file's own comment (cross-package dependency avoidance, D-64) — architecturally justified, but the two `deviationFactor`/`minBaselineOre` defaults (1.5 / 100) are duplicated as magic numbers in two files; a shared constants-only module (no service dependency) could remove that specific drift risk without violating the package boundary.

- **P3** `modules/growth/src/google-ads-transport.ts:334` — `fetchSpend` builds a GAQL query via raw string interpolation of `startDate`/`endDate` (validated via `DATE_PATTERN` regex first, so not an injection bug, but worth a one-line comment noting this is the only place the date validator's absence would matter) — already covered by strict `requireDateString`, no actual issue, listed only as a fragility note (no fix needed).

## `BusinessInternalSecretProvider` threat model

Sound. `BUSINESS_INTERNAL_CREDENTIAL_REF = "JARVIS_BUSINESS_INTERNAL_TOKEN"` resolves to a hardcoded, non-secret sentinel string (`"internal-no-external-credential"`) used solely to satisfy `ToolGateway.execute()`'s unconditional `credential = await secrets.get(ref)` requirement for tools with no real external provider (`business.*`, `growth.*` internal actions). It's never read from env, never logged as sensitive (correctly, since it isn't one), and `FallbackSecretProvider(env, new BusinessInternalSecretProvider())` ensures a real `.env` value (e.g., a future migration adding an external provider) would take precedence. No secret ever flows through this path. Confirmed via `credential.ts`, `RUNTIME_GATES.md`, and cross-module reuse (finance/governance/self-modification/owner-controls all reuse the same constant rather than duplicating the pattern).

## Health summary

The Business/Growth slice is unusually disciplined: RLS/tenant/space isolation is proven by dedicated Postgres-backed tests for essentially every write path, D-227 sweep-failure-isolation is applied consistently at the tenant-fan-out level, untrusted email/calendar content is provably kept out of authoritative memory (`business_activities.summary`), and doc/code drift is actively self-audited in-repo. The one real structural gap is intra-tenant rule-level failure isolation inside `OpenLoopService.runSweep()` (C-P2/D above) — one detection rule throwing can abort ~24 sibling rules for that tenant with no per-rule accounting, which is a meaningful gap against the codebase's own D-227 standard. `.env.example` is missing six scheduler-hour variables (P1, low severity since defaults exist). No P0 findings; no bugs, no tenant-isolation breaks, no secret leaks were found in either slice.
