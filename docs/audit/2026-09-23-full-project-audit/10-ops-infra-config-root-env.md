## A — Bugs / holes

**A1 (P2)** `ops/claude-worker/lib/trust.mjs:29-35` — `validateTrustedTask` (the trust gate for every `ARCHITECT_TASK`, i.e. the merge-authorizing path) checks only `comment.user.login === trustedAuthor`. It does **not** check `comment.author_association === "OWNER"`, unlike `validateControlCommand` (same file, line 135) which does for the supervisor's `ARCHITECT_CONTROL` commands. For a single-owner repo this is low-risk today (only the real `tsworkflow` account can post as `tsworkflow`), but it means the merge-critical path has a strictly weaker author check than the non-merge supervisor path, and a misconfigured `trustedAuthor` (e.g. naming a collaborator instead of the owner) has no independent role check to catch it. Fix: add the same `author_association !== "OWNER"` check to `validateTrustedTask`.

**A2 (P2)** `infra/local/docker-compose.yml` (voice-gateway service, lines 196-228) — the `voice-gateway` service has no `env_file: ["../../.env"]` directive (unlike `api`/`worker`/`migrate`). But `apps/voice-gateway/src/stt.ts:188-193` and `tts.ts:163-164` read `JARVIS_WHISPER_BIN`, `JARVIS_WHISPER_MODEL`, `JARVIS_WHISPER_LANG`, `JARVIS_PIPER_BIN`, `JARVIS_PIPER_MODEL` from `process.env`. None of these reach the container — local Whisper/Piper can never be configured for the compose-run voice-gateway; it silently falls back to the OpenAI-only STT/TTS path. Fix: add `env_file: ["../../.env"]` to the `voice-gateway` service, or add explicit `environment:` entries for the five vars.

**A3 (P2)** `infra/local/docker-compose.yml` — `infisical` and `langfuse` services have no `healthcheck:`. `api`/`worker` depend only on `migrate: service_completed_successfully`, not on `infisical`/`langfuse` being ready, so `api` can start and begin serving before the secret vault or tracing backend has finished booting. Given `InfisicalSecretProvider.available()` degrades gracefully (per `.env.example` comment), this is a soft gap, not a crash risk, but it means a "container healthy" state doesn't guarantee Infisical-backed secrets are actually resolvable yet.

**A4 (P3, unverified)** `ops/claude-worker/lib/task-admission.mjs` — not read in full. Header comment (read) documents the D-166 cross-worker lease design faithfully to the same create-if-absent/ledger pattern as `lock.mjs`, and its exports are wired correctly into `worker.mjs` (`acquireTaskAdmission`/`heartbeatTaskAdmission`/`releaseTaskAdmission`/`terminalizeTaskAdmission`/`inspectTaskAdmission`, all read in `worker.mjs`). I did not verify the 841-line implementation itself for the same void/released/EEXIST correctness `lock.mjs` earns through extensive comment-documented history — recommend it get the same adversarial-race review `lock.mjs` visibly went through (v2→v3→v2.3 in README), since it is structurally the newest and least battle-tested of the ledger primitives.

**A5 (P3)** `infra/local/docker-compose.yml` — every service with a `ports:` mapping (`postgres:5432`, `langfuse:3050`, `infisical:3060`, `api:3010`, `voice-gateway:3020`) uses the unqualified `"HOST:CONTAINER"` form, which binds to `0.0.0.0` by default. For a machine on a home/office LAN this exposes Postgres (admin password in `.env`), Infisical (secret vault) and the API on every network interface, not just loopback. Given CLAUDE.md rule 9 ("lokal først... kjøre i Docker på Tobias sin PC"), binding to `127.0.0.1:PORT:PORT` would be the safer default for a personal single-user deployment. Not flagged higher because it's a docs-declared "fase 1-stub" and NAS-portability (D-20) may deliberately want LAN reachability — but worth an explicit decision, not a silent default.

## C — Gaps

**C1 (P1)** The Windows-only worker/lock/crash-recovery test suite is not wired into `.github/workflows/ci.yml` (see B2). `build-test` runs `ops/*/test/**/*.test.mjs` on `ubuntu-24.04` only (`vitest.config.ts:23`); `windows-git-auth` runs two unrelated git-auth test files only (`ci.yml:70`). The lock ledger's NTFS-specific behavior (`EPERM`/`EACCES` on rename-over-open-file, documented extensively in `lock.mjs` and the README's "Runde 3/4" sections) is therefore **never exercised in CI** — only on Tobias's own host, manually, per the README's own admission. This is the single largest CI gap for a component CLAUDE.md marks security-critical.

**C2 (P2)** DB-backed tests: `vitest.config.ts` sets `fileParallelism: false` because "several test files start their own embedded PostgreSQL instance". None of `ops/claude-worker/test/*` need this (they're pure `.mjs`, no DB), but the **product** test suite (`apps/*/test`, `modules/*/test`) does, and per the task brief these fail with `initdb: Permission denied` in this sandbox — outside this slice's scope to fix, but worth noting that `build-test` in CI presumably has the permissions this sandbox lacks; I could not verify that CI itself passes these tests, only that the repo is structured to require them.

**C3 (P2)** `gitleaks` job (`ci.yml:72-93`) scans full history with `gitleaks detect --source . --no-banner -v`, no `--config`/custom rules file, relying entirely on `.gitleaksignore` for allowlisting. I reviewed all 5 entries in `.gitleaksignore`: each names an exact commit+file+rule+line, each has a written justification (Norwegian prose fixture, `finish_reason=length` string, synthetic HMAC test secret, deterministic idempotency-key fixture, Stripe object ID — never `sk_`/`whsec_`/`pk_` prefixed). None looked like they could plausibly hide a real credential from my reading; all are either non-credential fields or explicitly-labeled test fixtures. Not exhaustively re-derivable (I cannot re-run gitleaks here to confirm these are the *only* current findings), but the allowlist itself is not a blank check — it is line-anchored per commit.

**C4 (P2)** `postMergeEvidence.requiredChecks` in `config.example.json` (`["build-test", "windows-git-auth", "gitleaks"]`) matches the three real CI job ids in `ci.yml` exactly, and `DEFAULT_REQUIRED_POST_MERGE_CHECKS` in `postmerge-evidence.mjs:146-150` matches too. **But** `windows-git-auth` in this repo's actual CI only runs two narrow git-auth tests, not the Windows lock/worker suite (see C1) — so a merge gate requiring `windows-git-auth=success` is really only proving "git credential helper works on Windows," not "the worker's lock/admission ledger works on Windows." The required-check name is accurate to what CI actually runs; the CI job itself is the gap (C1), not this config.

**C5 (P2)** D-150/D-151 negative-case test coverage (task brief asked specifically about this): confirmed via grep — `test/durable-order-binding.test.mjs`, `test/admission-order-authority.test.mjs`, `test/authority-snapshot.test.mjs`, `test/merge-authority-immutability.test.mjs`, `test/worker-order-binding.test.mjs` all reference edited-comment (`updated_at`/`EDITED`) and ambiguous/forged-duplicate scenarios; `test/fixtures/fake-claude.mjs` has `JARVIS_FAKE_CLAUDE_FORGE_ORDER`/`FORGE_TASK_ID`/`ORDER_TAMPER` env-driven fault injection specifically to simulate a child forging a second `ARCHITECT_TASK`. **C6 (P3)** `bootstrap-databases.sql` / D-240 — the compose file's ordering (`db-bootstrap` depends on `postgres: service_healthy`; `langfuse`/`infisical` depend on `db-bootstrap: service_completed_successfully`) is correct and idempotent (`\gexec` guarded by `NOT EXISTS`). `migrate` depends only on `postgres: service_healthy`, not `db-bootstrap` — this is fine because `migrate` only touches the `jarvis` DB, which `POSTGRES_DB` already creates; no dependency is actually missing. ## D — Improvements

**D1 (P2)** `ops/claude-worker/lib/dispatch.mjs:452` — child `cwd` defaults to `cfg.repoPath` when `task.workspace` is absent ("a direct module call, and every pre-D133 test"). Since `worker.mjs` itself never dispatches without a workspace (confirmed by reading the full dispatch call site), this fallback is dead in production but live in the module's public API — a future direct caller (or a bug that skips `establishTaskWorktree`) would silently dispatch into the shared primary checkout instead of failing closed. Consider making `workspace` a required parameter with an explicit throw, rather than a silent fallback, given how much of this codebase's design philosophy is "no silent fallback."

**D2 (P3)** `infra/local/docker-compose.yml` — secrets (`JARVIS_DB_ADMIN_PASSWORD`, `INFISICAL_ENCRYPTION_KEY`, `INFISICAL_AUTH_SECRET`, `NEXTAUTH_SECRET`, `SALT`, `LANGFUSE_INIT_*_KEY`) are passed as plain `environment:` values sourced from `.env`, not via Docker secrets files or `env_file` isolation per-service. Acceptable for a documented single-user local dev "fase 1-stub," but worth a forward-looking note since CLAUDE.md rule 9 says the compose file should "flytte uten omskriving" (move without rewriting) to production-adjacent hosting.

**D3 (P3)** `ops/claude-worker/README.md` is 910 lines and extremely thorough — genuinely one of the best-documented modules in the repo, with every D-number cross-referenced to the exact code it fixed. No improvement needed on content; flagging only that its size makes drift detection (E-category) labor-intensive for future reviewers, since every C-rule claim requires cross-checking against a specific function.

**D4 (P3)** `.env.example` — 547 lines, extremely well-commented per-var, but has no machine-readable schema/validator (e.g. a small script asserting every var `loadWorkerConfig`/`configFromEnv`/`main.ts` requires is present with a comment). The env-var reconciliation gaps in section C-Env (45 undocumented vars) would be structurally prevented by such a script running in CI.

## 5-line health summary
The `ops/claude-worker` control-loop is exceptionally rigorously engineered for its stated threat model (self-forgery by the dispatched child, control-comment tampering, lock/admission races, crash windows) — every merge-gate claim in README's C1–C11 that I checked against code was accurate, and the 189 tests I ran passed. The one real security-relevant asymmetry found is A1 (ARCHITECT_TASK trust lacks the `author_association=OWNER` check that ARCHITECT_CONTROL has). The largest structural gap is C1/B2: the Windows-specific lock/crash-recovery test suite — the part of this codebase under the most scrutiny per its own README changelog — currently runs nowhere in CI. The env-var reconciliation found one dead var (`JARVIS_ENV`), 45 undocumented-but-real vars, and one concrete container-wiring gap (voice-gateway never receives its local Whisper/Piper config). Infra (compose/CI/gitleaks) is otherwise sound: no destructive git operations, no secrets in git history I could find reason to doubt, correct DB-bootstrap ordering, and clean main.ts/worker-main.ts default parity.
