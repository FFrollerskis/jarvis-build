## A. BUGS / LOGIC HOLES

### `src/service.ts`
- **P1 — service.ts:1709-1713** `submitVippsCapture` passes `current.amount_ore` (bigint→string) straight to `transport.capturePayment({ amountOre })`; `VippsTransport.capturePayment` (vipps-transport.ts:268) serialises it as `"value":"4000"` (JSON string, not integer). Vipps `modificationAmount.value` is an integer per the file's own contract; live capture will very likely be rejected (or, worse, coerced). Same at **1905** (`submitVippsRefund`). Never caught because the scripted fakes and `vipps-live.ts` accept any value; Vipps live gate is `PENDING_CREDENTIALS`. Fix: `amountOre: Number(current.amount_ore)` (as already done at 453/507/570) and add `Number.isInteger` guards in the transport.
- **P1 — service.ts:1054-1064 + stripe-webhook.ts:132-137** For `refund.*` events the envelope carries the *refund's* `amount`/`status`, but `ingestStripeWebhookEvent` feeds it to `applyStripePaymentOutcome`, which writes `provider_status='pending'`, `provider_reported_amount_ore=&lt;refund amount&gt;` onto the **parent payment intent**. A partial refund then trips `PROVIDER_AMOUNT_MISMATCH` (1274-1280) on the next sweep and the PI's `provider_status` no longer means "PaymentIntent status". Fix: only call `applyStripePaymentOutcome` when `envelope.object_type === "payment_intent"` (or a charge with `amount`), route refund objects solely to `applyStripeRefundOutcome`.
- **P1 — service.ts:1588-1592 + 1704** Vipps webhook writes `envelope.name` (`CAPTURED`/`REFUNDED`) into `provider_status` and the partial captured amount into `provider_reported_amount_ore`. Consequences: (a) after any `CAPTURED` webhook, `submitVippsCapture` refuses further partial captures (`provider_status !== "AUTHORIZED"` → `PaymentIntentNotAuthorizedError`) until a sweep refresh overwrites it; (b) `PROVIDER_AMOUNT_MISMATCH` false positive for partial captures (1949-1955). Fix: for `CAPTURED`/`REFUNDED` events do not overwrite `provider_status`/`provider_reported_amount_ore`; keep `AUTHORIZED` and only re-run settlement check.
- **P1 — service.ts:617-660 (+ fiken-transport.ts:159-183)** Fiken submit: the POST is inside the DB transaction, Fiken has no idempotency key (admitted at fiken-transport.ts:44-48), **and** `FikenTransport.request` retries POST on 429/500/502/503/504 up to 3× (line 177-180). A gateway timeout that actually posted the journal entry causes a second, third posting; a DB failure after a 2xx leaves the row `draft` and the next `submitPaymentIntent` posts again. Rule "retry cannot double-pay" is not met for Fiken. Fix: no automatic retry for non-idempotent POSTs; persist `state='submitted'` + attempt marker before the provider call; on retry reconcile by listing journal entries for the description/date before posting.
- **P2 — service.ts:436 vs 484/524/585/642** `assertValidPaymentIntentTransition(current.state, "submitted")` is only checked in memory; every branch writes `draft → provider_acknowledged` directly. The `submitted` state (state-machine.ts:25-26) is never persisted, so a crash between provider call and COMMIT leaves no trace that a provider mutation may have happened. Fix: write `submitted` (own short transaction) before the provider call, then `provider_acknowledged` after.
- **P2 — service.ts:1054, types.ts:377-385** `payment_intent.payment_failed` forces terminal `failed`, but Stripe's PI stays `requires_payment_method` and can still succeed later; the following `succeeded` webhook is then `WEBHOOK_STATE_CONFLICT` and Jarvis records a paid payment as `failed`. Fix: treat `payment_failed` as observational (`failure_reason` + flag), not terminal, or allow `failed → settled` only from this specific source.
- **P2 — service.ts:1798-1836** `cancelVippsPayment` after partial capture sets the intent `cancelled` although captured money exists (`vipps_captures.state='settled'`); refunds then become impossible (`createVippsRefund` requires `settled`, 1845). Fix: if `SUM(settled captures) &gt; 0`, transition to `settled` (partial) instead of `cancelled`, or block cancel.
- **P2 — service.ts:1724-1733** `submitVippsCapture` commits the capture as `settled`, then opens a **second** transaction for the `captured` event + `checkVippsFullSettlement`. If the second fails, the intent silently stays `provider_acknowledged` with no event, until a CAPTURED webhook arrives. Fix: do settlement check + event inside the first transaction (the FK deadlock reason cited at 419-428 does not apply here since the same `client` is used).
- **P2 — service.ts:590** Neonomics submit stores `amountOre`/`current.currency` (Jarvis's own values) as `provider_reported_amount_ore/currency`; the "provider-reported" columns are self-reported so PROVIDER_AMOUNT_MISMATCH can never fire for Neonomics. Fix: store NULL (transport returns no amount) and document.
- **P2 — service.ts:320-353** `createPaymentIntent` idempotency returns the existing row on key conflict **without comparing parameters**; a retry with a different `amount_ore`/`vendor_provider_ref` silently returns the old intent (test service-rls.test.ts:113 even asserts this). Stripe/Vipps both reject key reuse with different params. Fix: compare `amount_ore/currency/vendor_*/account_code` and throw `IdempotencyKeyParameterMismatchError`.
- **P2 — service.ts:1210-1215** `applyStripeRefundOutcome` `void`s `sourceEventEpochSeconds` — the JSDoc at 1209 and the file comment ("SAMME ordens-vokter-prinsipp") promise an ordering guard that does not exist. Fix: add `provider_status_updated_at` to `stripe_refunds` and compare, or fix the comment.
- **P2 — service.ts:770-782** `disableKillSwitch` discards `actorPersonId` (`void`), and neither enable nor disable writes any audit row. Disabling a class-D safety control is unattributed. Fix: add `disabled_by_person_id` column or a `payment_intent_events`-style audit table.
- **P2 — service.ts:891-898, 2068-2075; banking-service.ts:601-608** `appendAnomalyFlags` updates `WHERE &lt;id&gt; = $1` with no `tenant_id` predicate — RLS is the only isolation. Fix: add `AND tenant_id = $3`.
- **P3 — service.ts:417-418, 1176, 1696, 1815, 1892** Kill-switch read is not `FOR SHARE`; an `enableKillSwitch` committed after the read but before the provider call cannot stop the in-flight submission. Acceptable but undocumented. Fix: `SELECT … FOR SHARE` or document the window.
- **P3 — service.ts:634** Fiken posting date uses `toISOString().slice(0,10)` (UTC) — wrong bookkeeping date for Norwegian evenings after 22:00/23:00 local. Fix: format in `Europe/Oslo`.
- **P3 — service.ts:1108-1109, 1637-1638, 1848-1849** Refund/capture idempotency lookup is by `(tenant, idempotency_key)` only; the same key against another `payment_intent_id` returns the foreign row silently. Fix: include `payment_intent_id` in the check or throw on mismatch.

### `src/vipps-transport.ts` / `src/vipps-webhook.ts`

- **P3 — vipps-transport.ts:164-176, service.ts:168-169** `VippsTransport` caches the access token per instance but the factory constructs a new instance per call → token fetched on every operation (same for `NeonomicsTransport` via `defaultNeonomicsGatewayFactory`, service.ts:195-196, and `BankingService.gateway()` banking-service.ts:48-52). ## Health summary (5 lines)
1. Core domain (idempotent create, kill switch, state machine, RLS, vendor registry, spend integrity) is solid, well-tested against real Postgres, and typechecks clean.
2. Two P1 money-path bugs are real and untested: Vipps capture/refund send bigint-as-string amounts (live capture likely fails), and Stripe refund / Vipps CAPTURED webhooks corrupt the parent intent's provider fields (false anomalies, blocked partial captures).
3. Fiken is the weakest connector: retried non-idempotent POST inside the transaction, unverified request/response body shape, no live write ever executed — "retry cannot double-pay" does not hold there.
4. Every provider contract except Stripe is `VERIFIED_SEARCH_SNIPPET`; Neonomics direction-by-sign and silent `"0"` amount defaults could zero out or misclassify bank data unnoticed.
5. D-242 probes are wired end-to-end (transport → service → tool defs → registry), but untested at service level and the Fiken probe cannot run before the company slug it is meant to discover is configured.
